# Shared contracts: tasks 02A / 03B / 05B

Contract version 1. [domain.ts](../src/shared/domain.ts) owns records; [messages.ts](../src/shared/messages.ts) owns message shapes. [Synthetic examples](../tests/fixtures/contracts.examples.ts) cover an unnamed card, recurring meetings, a precise enrollment review, an activation request and a revision conflict. Task 02A established these compile-time shapes. Task 03B implements the schedule/settings runtime subset below; 07B enables timetable import; 10B enables only the provider-unconfigured lookup response; live retrieval, portal and enrollment execution remain later tasks.

## Ownership and compatibility

A owns timetable/editor consumers; B owns portal/provider adapters. Changes to shared records/messages need the other owner's review before integration. 03B implements schedule/settings validation and a single background writer against this contract. Browser setup and the pinned toolchain were completed in 03A. No portal selector, real school ID or provider endpoint is assumed here.

Persisted records use schemaVersion; transport uses protocolVersion. Both start at 1. Reject unknown versions with UNSUPPORTED_VERSION and leave saved data intact. A migration must explicitly read an old version and produce a validated new one; never reset a schedule because parsing failed. Unknown input enters validators as unknown, never through a type assertion.

## Implemented runtime subset (03B / 05B)

- `src/shared/validation.ts` parses CourseCard, Meeting, Schedule and DisplaySettings from unknown values into fresh records. IDs are bounded to 128 characters; controls and lone surrogates are rejected. Extra fields, accessors, prototype keys, invalid references/versions, duplicate IDs/occurrences and product limits are enforced. Other overlapping meetings are retained; 05B supplies derived conflict data consumed by the 06A meeting form and weekly grid.
- `src/shared/meeting-time.ts` (05B) parses exact HH:mm wall times, allowing 24:00 only as the end of the current day, and rejects nonpositive/overnight ranges. `findMeetingConflicts` revalidates a Schedule and returns deterministic pairwise overlap intervals without mutation. Intervals are [start, end), so adjacent meetings do not conflict; weekday occurrences remain independent. This derived API changes no stored record or RPC. See [05B evidence](evidence/05b-meeting-validation.md).
- `src/shared/foundation-rpc.ts` validates `schedule.read`, `schedule.save`, `schedule.import`, `settings.read`, `settings.save` and (10B) `professor.lookup`, including response schema and correlation. Lookup accepts only the provider-unconfigured result in this build. Reserved association/enrollment commands return `FEATURE_UNAVAILABLE` without parsing or executing those features. Unknown commands return `INVALID_INPUT`. Their domain-specific validators must be added with their owning feature tasks before enabling those commands.
- `src/background/handler.ts` verifies browser-supplied extension ID and the exact dashboard document URL (hash navigation allowed, queries denied), top-level frame and active lifecycle when supplied. Payload fields cannot self-authorize a sender. Popup, external-page and unsupported-document senders cannot read or write through this API.
- Invalid envelopes return `RpcRejection`: `protocolVersion: 1`, `ok: false`, a typed error and nullable `requestId`/`type`. These fields are null only when a valid envelope identity could not be parsed. A valid envelope, including an unsupported protocol version, retains its identity in the rejection.
- `src/storage/repository.ts` owns serialized reads and writes in one background instance. Keys are `uhd.schedule.<encoded ID>` and `uhd.settings`; versions are inside records so unknown versions cannot be accidentally hidden by switching keys. Missing schedules return NOT_FOUND. Missing settings return fresh defaults at revision 0 without writing; the first settings save expects 0 and persists revision 1. 05A uses the reserved UUID `48bdbce8-b801-4d5e-8748-35283d6803d7` for the single primary timetable and random UUIDs for new course cards. A stable primary ID allows dashboard windows to address the same schedule without a new discovery RPC or storage pointer. Other schedule keys are preserved; labels never identify records. Future multiple-timetable discovery needs a separately scoped contract. Imported/client revisions never dictate the stored revision.
- Every saved read is revalidated. Invalid/future records stay intact. Failed or uncertain writes do not trigger retries or resets. Revision checks, create-only semantics and successful-write events follow the rules below. 06B adds UI invalidation/refetch and non-destructive recovery. 07B implements export/import; schema migrations remain later scoped work; no unknown data is automatically repaired or reset.
- The worker restricts storage.local to TRUSTED_CONTEXTS before handling data. Only `storage` permission is requested. This excludes content scripts from direct storage access; trusted extension pages still technically have storage API access and must use the single-writer client by project convention.
- `src/shared/client.ts` supplies a typed dashboard client with runtime response validation, fresh request IDs and a 10-second reply deadline. It never retries automatically. `TRANSPORT_ERROR` means the outcome is unconfirmed; retain the draft and read authoritative state. An expired client timer does not cancel a worker operation.
- StateEvent notifications are best-effort metadata-only runtime messages emitted after persistence; a missing listener does not fail an already committed save. 06B listens to local storage changes by exact key, then refetches through the validated worker RPC. It does not consume notification payloads as data. Startup, focus, visibility and pageshow reads cover reconnects/missed notifications; events are not durable delivery or a replay protocol.

Enrollment activation deduplication and durable executor ownership still belong to 14B. This storage queue does not establish those guarantees and enables no enrollment action.

## Task 07B backup/import boundary

TimetableBackup remains schemaVersion 1 and timetable-only. parseBackup rejects extra/auth/job/provider fields, unknown versions, invalid references and duplicate occurrences. File bytes are capped at 1 MiB before JSON parsing; validated RPC backups also receive a serialized byte check. Export reads the authoritative schedule and constructs only the whitelisted backup shape. Display settings, planner data and unrelated storage are excluded.

The existing authenticated dashboard handler now enables schedule.import. The UI preserves the selected backup across navigation, blocks conflicting local edits, and invalidates preview when the saved snapshot changes. Failed/uncertain imports retain the preview, require explicit reload and refreshed review, warn about repeated-merge copies and never auto-replay. No enrollment action can be imported.

## Timetable mutation and import semantics

- The background writer serializes mutations. schedule.save compares expectedRevision with the current saved revision; a mismatch returns REVISION_CONFLICT without changing either copy. expectedRevision null means create only and fails if the ID already exists. A new record starts at revision 0; successful updates increment the stored revision by one. Never trust an imported/client revision as the next revision.
- The editor retains its unsaved draft on save failure/conflict. Offer reload/review rather than last-writer-wins overwriting. schedule.changed carries the authoritative revision; readers ignore old events and refetch on gaps.
- Backup export is constructed from the whitelisted TimetableBackup shape, not from all extension storage. No enrollment activation is possible through import.
- Import preview and confirmation happen before schedule.import. Both modes retain the local target schedule ID and increment its current revision. In 07B, expectedRevision also accepts null for a missing target, matching schedule.save create-only semantics: confirmation creates revision 0 and fails if another view created the target first. Preview/cancellation never creates an empty target. Replace adopts the imported timetable content/zone/labels but ignores its ID/revision. Existing data stays available if validation or writing fails.
- Merge requires matching timezones; otherwise reject and ask the student to choose replacement or adjust the source explicitly. Keep local labels and timezone. Generate new IDs for all imported courses/meetings and remap course references together; equal titles never imply equal identity. Show the resulting counts before confirmation, including any repeated import duplicates. Apply post-merge size limits. On a fresh target, adopt the imported labels/timezone and still generate new IDs for merge. Replace retains imported course/meeting IDs but never imported schedule identity/revision.
- Duplicate course makes a new independent ID. Add/remove a meeting changes only that occurrence. Editing a course updates every occurrence. Deleting a course removes its meetings in the same transaction. Missing field values remain blank; placeholders never persist as text.

## Message directions and authorization

Every dashboard request carries protocolVersion, requestId, type and payload. The response echoes requestId and type with either validated data or a typed error. No arbitrary selector, script, URL fetch or general-purpose execute command exists.

| Sender -> receiver | Allowed messages and checks |
| --- | --- |
| Dashboard -> background | DashboardRpc operations. Verify own extension ID and dashboard document URL from browser-supplied sender metadata. Only the enrollment review screen's explicit activation handler invokes enrollment.activate. A page cannot self-identify as the dashboard. |
| Background -> supported portal document | portal.inspect, portal.execute, portal.cancel. Target the verified tab/frame/document. Execute carries an exact reviewed selection and private job token. Reject stale/mismatched job or document identity. |
| Portal content script -> background | PortalReply only for an outstanding request from that exact tab/frame/document, matching requestId and job/token where applicable. Never accept a website postMessage as an enrollment command. Validate origin and adapter against the allowlist established by 01B. |
| Background -> subscribed dashboard | StateEvent only after successful persistence. Use safe EnrollmentJobView, never the internal EnrollmentJob. A changed-event notification cannot start an enrollment. |

Request IDs are unique per client operation. For enrollment.activate, persist its request ID and normalized payload with its job before acknowledging it. Repeating the same ID/payload returns the existing result, not another execution; reusing it with different payload returns REQUEST_ID_REUSED. Separate request IDs do not bypass the one-active-job rule. Timeouts require reading/reconciling the existing job, not generating a new activation ID automatically.

All other mutating operations use revision checks or defined idempotent association updates; read operations may be retried. A response timeout is not proof that the operation failed. Transport timeout durations and safe retention of the activation deduplication record are implementation decisions for 03B/14B and must be documented before execution is enabled.

## Exact enrollment review and lifecycle

1. Background inspects the selected supported tab and issues a review. Proposed review TTL: 120 seconds to activate, after which a fresh review is required. Once scheduled, the job retains its reviewed intent; at execution it must freshly compare the portal against that intent. The 120-second activation TTL must not accidentally limit how far ahead scheduling works.
2. Compute the review fingerprint in the background from a canonical JSON representation: verified target identity/adapter, termId, sorted complete section records (fixed key order, absent optional display fields normalized to empty strings), sorted selected IDs, and sorted deselect IDs. Use a cryptographic digest, not a hash supplied by the dashboard. Exclude timestamps and the fingerprint itself. Changing relevant page content invalidates the review. The fingerprint is a comparison aid, not a signature or sender-authentication substitute.
3. Activation supplies only reviewId, expectedFingerprint and timing. Retrieve the issued review, compare the token and current state, and generate job ID/execution token in the background. Reject stale or changed selections. Never accept a dashboard-authored EnrollmentJob or PortalTarget as execution authority.
4. Draft is editor state, not a persisted executable job. Active flow: armed -> preflight -> executing. Before dispatch, persist executor ownership/execution intent; repeated callbacks cannot submit again. Only one matching document may own execution. Restart or document loss before dispatch requires review; a crash around dispatch is unknown until reconciled.
5. Cancel before dispatch may transition armed/preflight to cancelled. The exact dispatch boundary is authoritative: a late cancellation returns TOO_LATE_TO_CANCEL and cannot trigger an auto-drop. A cancel acknowledgement must match the owning executor; do not show Cancelled merely because a message was sent.
6. Execution rechecks target, term, section identities, checkbox state and timing; apply the exact selection/deselection and submit once. Unknown dialogs or mismatches stop. Portal interaction details and whether scripting works are still 01B/G4 evidence, not part of this contract.
7. If no submission occurred, failure/cancellation/expiry may have no outcomes. After submission, normalize results to exactly the selected IDs. All enrolled -> succeeded. Any unknown -> unknown (retain known outcomes). Otherwise any enrolled or waitlisted -> partial unless all enrolled. All rejected -> failed. All waitlisted is partial, never successful enrollment.
8. Terminal jobs never auto-return to armed. A new attempt requires the student to inspect the portal and explicitly activate a new review. Do not retry an unknown submission, including after a worker restart or lost reply.

Runtime state transitions, durable execution ownership and late-job detection belong to 14B-18B. This task does not claim to have implemented or proved them.

## Task 14A timing-validation portion

`parseEnrollmentTiming(value, nowEpochMs)` in `src/shared/enrollment-timing.ts` validates the existing timing union and returns a detached record. It is currently a standalone module, not connected to any dashboard or runtime command; all enrollment RPCs remain FEATURE_UNAVAILABLE. This portion supplies no date picker, local-time candidate resolver, timer, job persistence or executor.

The caller supplies a trusted current epoch reading; do not take that clock value from an activation payload. Immediate mode permits only `mode: now`. Scheduled input requires all four timing fields, a valid named zone through the existing timezone validator, and an exact Gregorian `YYYY-MM-DDTHH:mm:ss` value in years 0001..9999. Offsets are signed integer minutes east of UTC, bounded to less than 24 hours in magnitude and checked against the actual zone. Timestamp and clock must be safe integers within JavaScript Date's range; scheduled timestamps must describe a whole second strictly after the supplied clock reading. No extra lead-time limit or timing tolerance is introduced here.

The local date is checked for rollover, then its explicit offset must produce exactly the supplied epoch. Formatting that epoch back through the specified zone, Gregorian calendar, Latin digits and 00..23 hour cycle must reproduce the input. A DST gap cannot satisfy the round-trip. Either occurrence of a repeated time can pass only with its matching explicit offset/epoch; missing offsets are rejected rather than guessed. Fractional-hour zones and half-hour transitions are supported at minute offset precision. Historical sub-minute offsets are not representable by this contract.

Malformed shapes, field types, zones and clock values return INVALID_INPUT; impossible calendar values, nonfuture targets and inconsistent timing values return INVALID_TIME. Extra fields, accessors and unexpected prototypes reuse the existing strict-record rejection. Future UI must turn these faults into actionable errors and make an ambiguous-time choice explicit. Future background activation must validate again against its own current clock and timezone database. This proposal parser must not be reused to reject expired stored jobs during recovery; stored-job reconciliation belongs to 14B. No timing, portal or submission gate is passed by structural validation.

## Task 14B stored-record validation portion

Job term/display label and selected-ID set must match the saved review. ## Task 14B activation deduplication portion

createForActivation(requestId, payload, candidate?) replaces unrestricted internal create(). It returns an internal job plus created: true for a new combined write, or created: false for a matching replay. Without a candidate it only resolves a saved request; an unknown request returns NOT_FOUND. A supplied candidate is validated and detached before queueing. Future trusted coordination must issue the review, job ID and token; this is not the public enrollment.activate handler.

The strict payload matches the existing RPC contract: reviewId, expectedFingerprint and timing. Normalization fixes object field order and detaches data; it preserves opaque IDs and explicit timing values, including timezone spelling. Unknown fields/accessors fail. parseEnrollmentTimingValue validates calendar/zone/offset consistency without a current-clock check so historical payloads can be compared. parseEnrollmentTiming still adds the future-target check for new proposals. The stored-job validator still checks timing against job creation.

Within the single-writer queue, a retained request is resolved before new-job freshness, active-job and capacity checks. The same ID and normalized payload returns its job's current state/revision, including cancelled, expired, needs-review or unknown; it does not return an old armed snapshot, write again, re-arm or dispatch. Different valid payload under that ID returns REQUEST_ID_REUSED. A new request must match its candidate's review ID, fingerprint and timing, and pass existing creation checks. Separate IDs cannot bypass one-active-job protection. Malformed payloads fail validation before lookup.

The same uhd.enrollment.jobs key now stores schemaVersion: 2 with jobs, activations and legacyJobIds arrays. Each activation has requestId, jobId and normalized payload. IDs and links must be unique; the payload must match the linked job; each job must have exactly one association or one explicit legacy marker. Missing/corrupt associations are not silently treated as legacy data. At most 100 jobs and associated entries are retained. No time-based deletion or eviction is implemented: associations survive terminal states, review/target expiry and restart for as long as the history remains. A full history rejects new creation but permits known replays. Future deletion/archive must preserve replay protection or explicitly redesign this policy.

Explicit recover() validates v1 records, stops active jobs and writes one v2 envelope with legacy markers for the original jobs. It cannot invent original request IDs or retrospectively deduplicate those jobs. Empty stored v1 envelopes migrate; absent storage still needs no write. A v1 envelope appearing after initialization blocks use until explicit recovery. Future versions and corrupt records remain untouched. Migration failure keeps operations blocked; a lost acknowledgment is resolved by re-reading the saved version rather than repeating a transition.

New request associations and jobs are persisted in one awaited set call. Recovery/transitions retain associations. A lost acknowledgment cannot produce a second job on replay after explicit recovery. This relies on the injected storage adapter's whole-value write behavior and one repository instance; synthetic tests do not prove cross-process locking or disk durability. No Chrome-storage/RPC wiring, authenticated executor ownership, live portal interaction or dispatch is enabled.
